## Key Decisions

1. **Quidli is a real, functioning, differentiated aggregator with near-zero independent traction.** It is the only product found that does multi-platform (8 handle-type) resolution plus a blended reputation score plus payment execution in one MCP call. Nothing else in this landscape does all three. But its adoption signal is minimal: 6 GitHub stars, 306 npm weekly downloads, 1-point/0-comment Show HN post (2026-09-09). **DO NOT use it to pay anyone.** Doc 2576, which called the live API, decided: "DO NOT pay a ZAO artist through Quidli. Not a pilot, not one test artist." and "USE nothing from Quidli for money movement". Its read-only-mirror opacity stands (real code lives in a private `sns-backend` monorepo you cannot audit). [Corrected 2026-10-07; this line previously said "USE it only where its narrow value ... is worth more than its unproven track record". See the correction note above.]
2. **ERC-8004 is not a competitor to Quidli - it solves a different, downstream problem.** It standardizes identity/reputation/validation for agents that already have an on-chain identity (minted ERC-721 `agentId`). It has no mechanism to resolve an arbitrary social handle to a wallet. Live-deployed on 17 EVM mainnets (verified independently on Basescan), Draft status as of 2026-09-29, but an independent academic study (arXiv 2606.26028) found only 3-15% of registrations are genuine live agents and 59-91% of reputation feedback is Sybil-flagged. DO NOT treat ERC-8004 as a substitute for handle resolution; DO treat it as a candidate identity layer to register ZAO agents into, once the Sybil problem is addressed.
3. **x402 is a payment rail, not an identity/reputation layer, and its headline adoption numbers do not hold up against registry-level measurement.** Wallet address IS the identity in x402 - zero mentions of "reputation," "handle," "ENS," or "social" in its 729-line spec. Vendor dashboard claims 75.41M transactions / $24.24M volume over 30 days (as of 2026-09-29); an independent snapshot of the same registry the same day shows $43,606 in Bazaar-listed GMV across 989,270 calls - roughly three orders of magnitude below the headline. USE x402 as the settlement rail underneath any of these tools; do not cite its headline volume numbers without the registry-level caveat.
4. **None of Agntor, Mu, or Larkin resolve social handles to wallets.** All three assume a wallet address already exists as the starting identity primitive. They compete with each other (trust scoring middleware, agent payment tooling, authorization middleware) but not with Quidli's core function. USE Larkin's pattern (receiver-side wallet reputation check, no private key needed) as a reference architecture if ZAO ever builds inbound x402 payment gating; SKIP Mu for anything requiring a private key held in an agent's own filesystem (`~/.mu/keys/wallet.seed`) without a human-approval option - its docs describe none.
5. **The free/existing resolution services (Neynar, Farcaster verifications, Lens) already do the CORE of what Quidli does, for free, for the specific platforms they cover - but only for people who already opted in.** Lens Protocol's public GraphQL API resolved a real username to a real wallet address with zero API key, live-tested in this research (`stani` → `0xAd2c0BEAdE60fb9f7ec5C87bDE8e4c126145F6E7`). Neynar resolves Farcaster (and, via a dedicated endpoint, X usernames linked through Farcaster) for free up to 10M credits/month. Quidli's differentiation is aggregating across MORE platforms (GitHub, Discord, Telegram, LinkedIn, email, phone) in one call, not doing something those free services fundamentally cannot.
6. **For the actual question - paying 8 festival musicians, some unbanked in crypto, one with no social media at all - no product in this landscape solves it, and Quidli does not either.** The free mechanisms reviewed (Neynar, Lens, Farcaster verifications) require the payee to already hold BOTH a wallet AND a linked/verified account somewhere. Quidli is different, and worse for this purpose: doc 2576 measured `connect_lookup` returning never-used addresses (nonce 0 and zero balance on both Base and Ethereum) for `github/torvalds` and `twitter/jack`, in the same response shape as a real used wallet, and quotes the founder that his agent "resolves all github accounts to wallets generated for those users via quidli". So Quidli does return an address for a handle with no wallet, and the caller cannot tell a generated address from one the payee controls. [Corrected 2026-10-07; previously "Every mechanism reviewed (Quidli included) requires the payee to already hold BOTH a wallet AND a linked/verified account".] A musician with no social media has no handle to feed into any of these systems, full stop - this is a structural gap, not a feature gap, and it cannot be closed by better handle resolution. See Finding 7 for the concrete real-world options.

## Findings

### 1. Quidli, what it actually is (verified against live production API and code, not just the task description)

Quidli's real repo is `github.com/Quidli/connect-mcp` - but it is explicitly **a read-only mirror**, regenerated on every npm release from a private monorepo called `sns-backend`; the mirror's own CONTRIBUTING.md says PRs against it are destroyed on the next sync. [FULL, method: `gh api`] This matters for due diligence: you can read the shipped MCP-server code, but you cannot audit the scoring logic or the `connect_drop` execution path beyond what's exposed at the API boundary.

Calling the live production MCP server directly (`https://mcp.connect.quid.li/`, JSON-RPC `tools/list`) returned **14 tools**, not the 9 described in the task brief or the 10 documented in the README - 4 of them (`connect_trust_create`, `connect_trust_revoke`, `connect_trust_check`, `connect_trust_graph`) are undocumented in the README and build a separate, EAS-based (Ethereum Attestation Service) on-chain "trust graph" on Base, gated by API key and gas-metered in ETH. [FULL, method: direct curl to the live endpoint] Quidli is shipping ahead of its own docs.

The actual reputation-score inputs, read from the live schema (`src/schemas.ts`), are `quidli_score` (0-100, Quidli's own composite), `lens_score` (0-1), `neynar_score` (0-1, i.e. Farcaster), and `ethos_twitter_reputation` / `ethos_wallet_reputation` (0-2800, from the third-party Ethos protocol) - **not** "GitHub contribution history, X engagement, Discord participation... phone and email" as described in the task brief. GitHub/Discord/phone/email appear only as *lookup identity types you can search by*, not as named score inputs; whether the internal `quidli_score` blends those signals is UNKNOWN, since that logic lives in the private `sns-backend` repo. [PARTIAL, method: read `src/schemas.ts`/`src/tools/register.ts` from the mirror via `gh api`, then flagged the unauditable gap]

Live chain support (`GET https://api.connect.quid.li/chains`, unauthenticated) is broader than the "Base or Solana" framing: **Ethereum, Base, Polygon, OP Mainnet, Arbitrum One, Avalanche, World Chain (+ Sepolia testnet), and Solana** - 8 chains total, all supporting both lookup and drop. `connect_drop` can send any native token or ERC-20/SPL token, not just USDC. [FULL, method: direct curl to production API]

The private key question, answered precisely: the EVM private key used for x402 pay-per-call is **the calling agent's own key**, held only in local/stdio mode, and the README explicitly instructs "do not send a private key to the hosted endpoint" - the hosted server has no path for key-based auth at all. This is Quidli's own claim (README text), and this research did not independently audit the signing code (`src/x402-fetch.ts`) to verify no key material leaves the local process, so treat the "never leaves your machine" framing as VENDOR CLAIM, not independently verified. [PARTIAL, method: README read via `gh api`, code file listed but signing logic not fully read] **Corrected 2026-10-07:** doc 2576 audited the client source after this was written. It found "No spend cap in the client. `x402-fetch.ts` calls `wrapFetchWithPayment(fetch, client)` with no maximum", and that `CONNECT_API_BASE_URL` is env-overridable, so "an x402-enabled instance signs payment for whatever a `402` from the configured host asks". That audit is about spending. It does not settle whether key material leaves the local process, so the "never leaves your machine" framing is still a vendor claim.

npm package `@quidli/connect-mcp`: 18 published versions since first publish 2026-06-18, latest 0.6.3 (2026-09-21), MIT license confirmed matching the GitHub LICENSE file. Weekly downloads **306**, monthly **1,254** (control check against `react` in the same week returned 203,157,609 - confirms the API works and Quidli's number is real, not a broken query). [FULL, method: `registry.npmjs.org` + `api.npmjs.org` JSON APIs]

### 2. ERC-8004: Draft status, live but low-quality reputation registry, solves a different problem than Quidli

Status confirmed directly from `eips.ethereum.org/EIPS/eip-8004`: **Draft**, created 2025-08-13, authored by people from MetaMask, Ethereum Foundation, Google, and Coinbase. [FULL, method: curl+strip of the live EIP page]

Contrary to a naive reading of "draft" as "not deployed," the Identity and Reputation Registries ARE live, deployed via deterministic CREATE2 at identical addresses (`0x8004A169...` Identity, `0x8004BAa1...` Reputation) across 17 EVM chains including Ethereum mainnet and Base - independently confirmed on Basescan (a real contract, creator address visible, "AgentIdentity (AGENT)" token tracker entry, deployed roughly 238 days before this research, consistent with a February 2026 deployment). [FULL, method: curl of a third-party block explorer, cross-checking a promotional third-party indexer's claim] Validation Registry is mainnet-pending, testnet-only, per the same indexer.

ERC-8004 **does not resolve a social handle to a wallet and was never designed to.** Its Identity Registry is "a minimal on-chain handle based on ERC-721... that resolves to an agent's registration file" - the agent must already mint an on-chain `agentId` NFT before it has any identity. There is no field anywhere in the spec for an X username, a Farcaster handle, a phone number, or an email address that isn't already tied to a registered agent. [FULL, method: curl+strip of the EIP spec text, cross-checked against contract function signatures]

Adoption is real in volume but poor in quality per an independent academic measurement (arXiv 2606.26028, "Can Trustless Agents Be Trusted? An Empirical Study of the ERC-8004 Decentralized AI Agent Ecosystem," crawled Ethereum/BSC/Base through 2026-05-13): only **3%, 4%, and 15%** of registrations across those three chains expose a valid registration file with at least one live service endpoint - the rest are placeholders. On the Reputation Registry specifically: **73.5%, 59.2%, and 90.6%** of reviewers across the three chains show coordinated Sybil behavior; after removing Sybil-flagged feedback, **15.8%, 77.9%, and 86.8%** of rated agents are left with zero valid feedback. The paper's own conclusion: "the Registry, as currently deployed, cannot function as a trust signal." [FULL, method: curl+strip of the actual arXiv abstract text - this is the single strongest data point in this whole research pass]

The reference implementation with the most independent tooling built around it is ChaosChain's (`ChaosChain/trustless-agents-erc-ri`, 54 stars) though the most-starred contracts repo is the canonical `erc-8004/erc-8004-contracts` (237 stars, 114 forks). A broader ecosystem of 15+ SDKs/tools exists (Rust, TypeScript, Vyper, TEE extensions) per `gh search repos "ERC-8004"`, showing real multi-team investment even though the arXiv study says most registered agents behind it are inactive. [FULL, method: `gh api`/`gh search`]

**Bottom line for the synthesis:** ERC-8004 and Quidli are not substitutes. ERC-8004 standardizes trust/discovery for agents that already exist on-chain; Quidli's `connect_lookup` solves the upstream, different problem of going from a not-yet-onboarded Web2 identity to a wallet in the first place. Quidli's own undocumented `connect_trust_*` tools are a smaller-scope, EAS-based analogue to what ERC-8004's Reputation Registry is trying to standardize - worth flagging as a place where Quidli is quietly building its own mini version of ERC-8004's reputation layer rather than integrating with it.

### 4. Agntor, Mu, Larkin: none resolve social handles; each takes a different position on the private-key / human-approval axis

All three were confirmed as the correct products (not name collisions) and none of them do social-handle-to-wallet resolution - every one assumes a wallet address (or, for Agntor, an optional wallet) is the starting point. [FULL for all three, method: HN Algolia thread + comment fetch, then curl of the actual linked landing page/docs, then `gh api` for repo stats and actual LICENSE file text]

- **Agntor** ("Trust infrastructure for AI agents: identity, escrow, guard," Show HN 2026-02-17, 2 points, the sole "comment" being the OP's own post text - zero third-party replies). Its docs explicitly state a wallet is optional ("+4 identity points" if provided, escrow can run database-only without one) and it supports a configurable `requireHumanApprovalAbove` spend-policy threshold alongside fully autonomous operation - the only one of the three offering a documented human-in-the-loop option. GitHub: 11 stars, MIT license (verified), last pushed 2026-03-21 - effectively dormant since roughly a month after launch, with zero HN mentions of the product since Feb 2026. A domain anomaly was found: the bare `agntor.com` domain currently serves an unrelated product ("HireBot.lol," a job board for hiring AI-agent contractors) while `app.agntor.com` and `docs.agntor.com` still serve the trust-infrastructure product - unresolved whether this is squatting on a dropped domain or a pivot; flagged as UNKNOWN.
- **Mu** (micro.mu, "Tools for Agents with x402 payments," Show HN 2026-08-13, 3 points, 0 comments). This is the one product of the three with a **mandatory local private key**: setup instructions write a wallet seed to `~/.mu/keys/wallet.seed` and the paying-agent code example reads `EVM_PRIVATE_KEY` directly from the environment into an autonomous payment loop, with **no human-approval step described anywhere** in the fetched docs - the only stated safety rail is a max-loop-step cap. USDC on Base only. GitHub (`micro/mu`): 437 stars, AGPLv3 (verified), pushed literally today (2026-09-29) - the most actively maintained of the three by a wide margin, and part of a multi-year, sustained HN presence under the broader "Micro" project (85 related HN hits since 2020), even though this specific x402 post itself got almost no engagement.
- **Larkin** ("Authorization middleware for x402 agent payments," Show HN 2026-04-30, 1 point, 0 comments). Structurally the opposite of Mu: it is **receiver-side** middleware that a paid API installs to score the *paying* wallet's reputation (5-dimension score, Ed25519-signed receipt, sub-200ms) and decide BLOCK/WARN/SURCHARGE - it never touches a private key on either side because it only consumes a wallet address as input. No human-approval option is offered; all three decision modes are fully automated. Pricing is public (free tier 10,000 checks/month, $29/mo for 500K, $199/mo for 5M). GitHub: 1 star, MIT core (scoring service itself closed-source), last pushed 2026-07-26 - some post-launch activity but stale relative to today, and zero follow-up HN mentions in the ~5 months since launch. Notably built "in 10 days with Claude Code" per its own footer.

### 5. Free handle-to-wallet resolution: covers the same core function as Quidli, for free, but only for people who already opted in on that specific platform

- **Neynar** resolves Farcaster FIDs to verified ETH/SOL addresses (`verified_addresses.eth_addresses[]`/`.sol_addresses[]`) and, via a dedicated `by_x_username` endpoint, an X/Twitter handle to the Farcaster user (and thence their wallets) - but ONLY if that person has explicitly gone through Farcaster's on-chain verification flow or linked their X account. Coverage is opt-in, not universal (example unverified users in Neynar's own docs show empty address arrays). Has a real reputation signal, `neynar_user_score` (0-1), plus a `power_badge` anti-spam flag. Requires an API key for real use (confirmed live: an unauthenticated call to `api.neynar.com` returned HTTP 402 "X-PAYMENT header or API key required"); free tier is 10M credits/month, 600 requests/minute. [FULL, method: live API call + official docs]
- **Farcaster's own protocol-level verifications** are an explicit, opt-in, EIP-712-signed action (a `VerificationAdd` message), capped at 25 addresses per FID - confirmed from the raw protocol spec. What percentage of Farcaster accounts actually have one is UNKNOWN in this research: the relevant Dune tables were identified (`dune.neynar.dataset_farcaster_fids`/`verifications`) but this session's Dune access is read-only and two attempts to execute a count query both failed with "Your account is read-only" - a BLOCKED measurement, not a zero, and it should not be read as "coverage is low" or "coverage is high." [BLOCKED, not guessed]
- **Lens Protocol** genuinely works, for free, with no API key, right now: a live test query against `api.lens.xyz/graphql` resolved the username `stani` to `0xAd2c0BEAdE60fb9f7ec5C87bDE8e4c126145F6E7` with zero authentication. [FULL, method: live, unauthenticated GraphQL call - this is the single cleanest "free alternative to Quidli" finding in this whole research pass, for the subset of people who have a Lens account.] Same opt-in limitation as Farcaster/Neynar: only covers people who created a Lens account.
- **ENS resolves in the wrong direction for this use case.** It takes an ENS NAME (`someone.eth`) and returns an address - it does not take an arbitrary social handle like `@someone` and return anything. ENS text records CAN store a Twitter/GitHub handle as optional metadata on a name someone already owns and configured, which is the opposite direction from what's needed (you'd need to already know their ENS name to look up their Twitter handle, not the reverse), and that metadata is self-reported, not independently verified by ENS. Coinbase's Basenames (an ENS fork on Base) has the identical limitation. [FULL, method: curl+strip of ENS's own docs]
- **Coinbase cb.id appears discontinued as of this research.** `cb.id` 301-redirects to a generic Coinbase Wallet marketing page containing zero occurrences of the string "cb.id" anywhere in the HTML. [FULL for the live redirect/content check; note this is not proof of a formal deprecation announcement, which was not separately searched for]
- **GitHub and Discord have NO native wallet field at all, confirmed against their own official APIs/specs** - GitHub's `social_accounts` endpoint has no crypto/wallet provider type; Discord's entire `ConnectedAccountProviders` enum (24 platforms) has no wallet type either, and Discord's connections API can only ever read the calling user's OWN connections, never look up someone else's by ID or handle - so even if a wallet field existed, there would be no way to query it for a third party. [FULL, method: GitHub REST API live call + Discord's own published OpenAPI spec, grepped for zero occurrences of "wallet"/"crypto"/"ethereum"] Telegram and LinkedIn were not fully checked - both UNKNOWN, not confirmed NONE.

### 6. Direct comparison of the private-key / human-approval axis (the distinction you asked to be tracked closely)

| Product | Private key location | Human approval available |
|---|---|---|
| Quidli | Agent's own key, local/stdio mode only (vendor claim; doc 2576's audit: no spend cap in the client - corrected 2026-10-07) | Not a built-in flow |
| x402 (protocol itself) | Self-held OR Coinbase-managed TEE via "API key wallets" | Caller-side integration choice, not protocol-native |

Only Agntor documents an explicit, configurable human-in-the-loop threshold. Every other product in this landscape either requires a key somewhere in the flow with no approval gate (Mu, and x402 by default), sidesteps the key question entirely by being receiver-side (Larkin), or leaves the approval question to whatever the integrator builds on top (Quidli, x402 generally, ERC-8004).

### 7. The actual question: paying 8 festival musicians, some unbanked in crypto, one with no social media at all

This is the honest finding the task explicitly asked to allow: **this class of product does not solve that problem, and being honest about which piece of it does and does not apply matters more than a single verdict.**

Break the 8 musicians into the realistic subgroups:

- **Musicians with a crypto wallet AND an already-verified social account somewhere (Farcaster, Lens, or linked through Quidli itself):** the FREE services (Neynar, Lens) already solve this for zero cost, for the specific platform they're verified on. Quidli adds value here only if the payer wants one MCP call across many platforms instead of separately querying Neynar/Lens/etc., or if the musician's verification lives on a platform (GitHub, Discord, Telegram, LinkedIn, phone, email) that has no free equivalent - GitHub and Discord were confirmed to have literally no wallet-lookup capability at all, native or third-party, so for THOSE platforms specifically Quidli (or a bespoke build) is the only handle-resolution option found in this research, PROVIDED the musician has separately registered/verified with Quidli or a service it aggregates. [Corrected 2026-10-07: per doc 2576 the lookup response does not say whether a returned address is the musician's own or one generated for them, so even this case cannot be relied on for a payout.]
- **Musicians with a crypto wallet but NO verified link anywhere (Quidli included):** no product in this landscape - paid or free - can resolve a handle for someone who has a wallet but hasn't linked it anywhere discoverable. The organizer has to ask the musician directly for their address. Quidli does not fail here, and that is the problem: per doc 2576 it returns a generated, never-used address for such a handle, with nothing marking it as generated, so the money would not reach the wallet the musician already holds. [Corrected 2026-10-07; previously "This is true for Quidli too", meaning it also needed a linked wallet.]
- **Musicians with a social handle but NO crypto wallet at all:** the free mechanisms (Neynar, Lens, Farcaster verifications) require a wallet to already exist and be linked. Quidli does generate one: doc 2576 measured it on-chain and quotes the founder ("wallets generated for those users via quidli"). Paying such a handle could, in doc 2576's words, "park the money at an address they have never touched, pending a claim flow, with no signal in the response that this is what happened". [Corrected 2026-10-07; previously "none of these products create a wallet for someone who doesn't have one", with the `connect_drop` mechanism "flagged UNKNOWN". It is no longer unknown.] The realistic organizer path here is a standard fiat rail (ACH, Venmo, Zelle, PayPal, a check) or walking the musician through creating a wallet manually - outside the scope of every product surveyed.
- **The musician with NO social media presence at all:** by definition, there is no handle for ANY of these systems - free or paid - to resolve. This is not a coverage gap any handle-resolution product can close, because the entire category's input requirement (a handle) does not exist for this person. The only real options are traditional payment rails entirely outside this product category: cash, check, direct bank transfer/ACH with manually collected account details, or a payment app (Venmo/Zelle/PayPal) using their name/phone/email collected directly, not looked up.

**Honest bottom line:** for a real festival payout to 8 musicians with mixed banking status, the organization should expect to run a MIXED payment process - crypto-native handle resolution (the free services where they apply; not Quidli, per doc 2576 - corrected 2026-10-07) for the subset who are already crypto-native and linked somewhere, and ordinary fiat rails for everyone else, including anyone with no wallet and, necessarily, the musician with no social media at all. No product surveyed - including Quidli - closes that gap; Quidli's value is narrowly in reducing the crypto-native subset's friction from "collect 5-8 separate wallet addresses by DM" to "one MCP call across many platforms," which is a real but modest convenience, not a solution to the unbanked/no-handle case.
