# 2538 - Improving the Paragraph AI writing agent workflow for the ZAOstock daily newsletter

> **Goal:** Answer four concrete questions raised in the 2026-09-22 (Day 265) session driving Paragraph's AI agent for the "Year of the ZABAL" daily newsletter: is auto-cover-generation real and controllable, how to stop the agent replying in chat instead of the draft panel, how to stop it fabricating past tense for future events, and what else Paragraph's own docs/changelog/community say about the agent's limits.

## Findings

### 1. Auto-thumbnail/cover generation - real feature, not spontaneous

Paragraph's editor documentation (`docs.paragraph.com/publishing/editor`, fetched FULL 2026-09-22) describes exactly three ways a cover image is created:

1. **Upload** - manual, unchanged from the old manual playbook.
2. **Generate** ("Choose Generate and Paragraph draws a couple of options from your post, matched to the look you already run") - user clicks a button.
3. **Choose style** - user picks a named art direction and Paragraph generates options in that style.

None of these is "spontaneous, unrequested generation appearing in a draft preview." The closest documented trigger for an *unrequested* cover appearing is the agent's **pre-publish readiness flow**: "When a draft feels close, ask your agent to help you get it ready to publish. It reviews the post and surfaces... A settings recap where you can adjust the slug, canonical URL, visibility, author, newsletter audience, and cover in place." If a cover did not exist yet at that point, it is plausible the readiness review generated one as part of surfacing a complete settings recap - this is the most likely mechanism for what looked unprompted today, though it was not directly confirmed against today's exact prompt text.

The **automatic** part Paragraph explicitly ships (changelog `Style-matching headers, instant prompts, and faster custom sites`, dated 2026-07-07, fetched FULL) is style-matching, not generation-triggering: "we've... made custom image styling automatic... When generating new cover images, the assistant automatically references your past published covers to match your unique color palette, style, and visual treatment." This is genuinely new capability (shipped roughly 2.5 months before today's session) and explains why a generated cover, once triggered, now looks more "in your brand" without being told the palette - it does not explain unrequested triggering.

Paragraph's blog post introducing its nine-agent "fleet" (`Meet the Agent Fleet Behind Your Content Engine`, published 2026-09-08, fetched FULL) confirms cover generation is owned by a dedicated **Media** sub-agent ("Generates and edits images: post covers, social cards, illustrations"), separate from the **Writing** sub-agent that drafts body text, and separate from **Publishing** (runs the pre-publish review). Multi-step requests execute the sub-agents "in a precise order," which is consistent with a single "get this ready" style prompt cascading into both a Writing pass and a Publishing-triggered Media pass without the cover being separately requested.

No Reddit, Hacker News, X, or Discord discussion of this specific behavior (auto/unprompted cover generation) was found - searched directly (see Sources); this is a documented negative result, not an exhaustive absence.

### 2. Draft-vs-chat targeting failure

Paragraph's own docs describe the UI as intentionally two surfaces sharing one document: "Drafts and agent edits live in the same document. When your agent works on a post, you'll see its changes in the editor... While chatting, the post opens in a side panel next to the conversation, and you can expand it into the full editor at any time." (`docs.paragraph.com/publishing/editor`, FULL.)

This directly corroborates - and gives Paragraph's own architectural language for - the failure mode already documented in this project's own newsletter skill (`~/.claude/skills/newsletter/SKILL.md` lines 156-159): "The draft is ONLY in the right-hand editor panel. `get_page_text` returns the CHAT, never the draft. Judging the draft from the chat reply is how the fabricated builder count survived three passes."

No Paragraph-specific community report of the agent replying with full body text in chat instead of writing to the draft was found on Reddit, HN, X, or Paragraph's Discord (searched, no hits - documented negative result). The closest verified community analog is from a different agentic coding tool with a structurally similar architecture (a chat pane plus a separate draft/composer surface): Cursor's own forum documents two confirmed, tracked bugs in its "Agents pane" - "the caret jumps and text randomly gets inserted or deleted while typing" and "drafts leak between panes and don't persist when switching" - which a Cursor engineer confirmed as "known bugs... both on our side," with an interim workaround of "send the draft or copy it somewhere else... before you switch tabs" (`forum.cursor.com/t/agents-pane-text-preservation/164488`, fetched FULL, thread opened 2026-07-01, fix shipped and confirmed working by 2026-08-31). This establishes the general pattern - chat/draft desync in agentic writing UIs is a known, recurring class of bug across products, not unique to Paragraph or to this project - but it is not proof of Paragraph's specific mechanism.

No documented Paragraph-specific prompt pattern exists to force the agent to write into the draft rather than reply in chat. The docs' own example phrasing for the intended flow is a direct instruction, not a question: `"Help me outline a post about what I've been working on lately"` is presented as the trigger that lands text in the editor. RECOMMENDATION (inferred, not documented): phrase draft-writing requests as imperatives ("Write the full post body now" / "Put this in the draft"), not questions or discussion ("What should today's post say about X?"), since the latter more plausibly reads to the orchestrator as a request for a chat answer rather than a write action. This is a hypothesis to test against future occurrences, not a confirmed fix.

### 3. Past-tense fabrication for future/pending events

No Paragraph-specific documentation, changelog entry, or community report addressing this failure mode was found. This is the general LLM temporal-hallucination problem, and the best documented practices come from general agentic-writing and LLM-hallucination research, not from Paragraph:

- **Prefix placement beats suffix placement, and explicit beats implicit.** A 2026-05-14 study (alphaXiv 2605.14636, "Teaching Large Language Models When Not to Know: Learning Temporal Critique for Ex-Ante Reasoning," fetched FULL via search highlights) measured that "explicit cutoff statements outperform implicit historical framings, and prefix constraints reduce leakage more effectively than suffix constraints" and that models are "reacting to specific patterns of words in the instruction" rather than genuinely reasoning about the cutoff - meaning a cutoff/pending-status statement buried after the facts, or phrased softly ("don't invent facts"), is measurably weaker than one stated as the first sentence in explicit terms ("As of [date], X has NOT happened").
- **Prompt engineering alone does not guarantee compliance.** The same study's conclusion: "prompting can steer models into a temporal frame, but does not endow them with the ability to verify whether a response is temporally admissible" - the fix trains a model to critique its own temporal admissibility (TCFT), which is not available inside a hosted product like Paragraph; for a prompt-only workflow, the mitigation is procedural (see below), not a magic phrase.
- **Negative instruction + explicit "if uncertain, say so" framing measurably reduces fabrication** (Promptyze, "LLM Hallucination Detection and Prevention: 2025 Complete Guide," fetched FULL via search highlights): explicit forbidding language ("Do NOT invent... Do NOT make confident claims about uncertain information... If you don't have information, say: 'I don't have information about [X].'") combined with **temporal context specification stated as a boundary** ("All information in this prompt reflects the state of the company as of [date]. Do NOT assume any changes occurred after [date].") is the documented pattern for this exact class of error ("This prevents temporal hallucinations where the model invents recent events").
- **A confidence gate (procedural, not just prompt text) catches what phrasing alone won't.** Woyable's 2026-07-07 production hallucination guide (fetched FULL via search highlights) reports a measured production result: adding an explicit refusal path ("Answer using ONLY the context below... If the answer is not in the context, reply exactly: 'I don't know.'") on top of grounding "cut confident-wrong answers by roughly another third." Applied to newsletter drafting: for any fact whose completion status is pending, the prompt should give the agent an explicit escape hatch to flag it as unresolved rather than force it to write a sentence about it at all.

PRACTICAL SYNTHESIS for the ZAOstock prompt pattern: put the pending/future fact status as the first sentence of the prompt, in explicit tense-bearing language ("The [bounty] deadline is [date], which has NOT occurred yet as of today [date]. Write about it only in future or present tense. If you are unsure whether an event has concluded, write 'TBD' and flag it - do not guess.") rather than a general end-of-prompt disclaimer. This is inferred from the general research above, not verified against Paragraph specifically, and should be tested against the next draft with a pending fact before being treated as solved.

### 4. Other documented Paragraph agent limitations/quirks (STANDARD tier survey)

- **The agent is a fleet, not one model.** Nine named sub-agents (Writing, Publishing, Media, Video, Website, Social, Research, Scheduling, Brand) share one memory of "voice, goals, and notes" but each is scoped to its own tools; a single request can cascade across several of them in sequence (`paragraph.com/@blog/meet-the-agent-fleet-behind-your-content-engine`, FULL). This matters for prompt design: a compound request ("write today's post and generate a cover") is not one model doing two things, it is an orchestrator handing off between two sub-agents with a shared memory but separate judgment - each hand-off is a place fidelity to the exact prompt wording can drift.
- **Nothing publishes without explicit approval**, per Paragraph's own docs, across every surface checked (editor docs, features/draft FAQ, X Articles blog post): "Nothing publishes until you say so. Your agent always asks before anything goes public." This is consistent with, and independently confirms, this project's own Mode B rule 5 ("It never publishes on its own, and neither do you. Publishing is Zaal's.").
- **Paragraph has shipped and fixed chat/publish-flow bugs before.** The 2026-06-11 changelog (`website-themes-and-smarter-analytics`, FULL) lists among its fixes: "Fixed an error that could appear when prepping a long post for publishing from chat." This is direct evidence from Paragraph's own release notes that chat-driven publish-prep is a genuinely fragile code path on their end, not purely a prompting problem.
- **A second, independently confirmed rendering defect already exists in this library.** Doc `business/2528-paragraph-beyond-the-post-sept2026` (2026-09-21, this repo) reproduced a live "two-route rendering defect" where Paragraph's own OpenAPI spec documents the buggy canonical URL route (`@[publicationSlug]/[slug]`) rather than the working `/writing/` route. Combined with today's findings, this establishes a pattern: Paragraph's AI-native surface (agent, cover generation, canonical URLs) is shipping fast (multiple dated changelog entries between April and September 2026) and has multiple independently-confirmed rough edges, not just the three raised in this session.
- **No public API existed as recently as the product's early web3 era** (`docs.paragraph.xyz/docs/development`, "We don't have a full, public-facing API yet"); this is now stale relative to docs 2527/2528, which confirm a working REST API and MCP server exist as of September 2026 - noted here only to flag that older cached documentation pages for Paragraph are unreliable and should not be trusted without a date check.
- **No Reddit, HN, or Discord community thread specifically about Paragraph's AI writing agent's reliability was found** in this research pass (multiple targeted searches, see Sources) - documented as a negative result. Paragraph's community footprint on these platforms is thin relative to mainstream coding-agent tools (Cursor, Claude Code), which is itself informative: bugs in this product are more likely to be discovered internally by ZAO than crowd-sourced from public discussion, so this project's own incident logs (the newsletter skill's "operating manual" section, and doc 2528's rendering-defect report) are currently the most complete record of Paragraph agent quirks that exists anywhere checked.
